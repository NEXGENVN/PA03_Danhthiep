# Giao diện đầy đủ để xem PA03

## Intent

User asks to add enough UI for all existing features to inspect the application. Existing input contains 73 JS files but no HTML/CSS. Preserve recovered business code and build a separate local interface covering the 31 feature groups in docs/FEATURE-MATRIX.vi.md.

## Direction and builder decisions

Vietnamese workspace dashboard, dark navy sidebar, warm white canvas, teal accent, system fonts, compact readable tables, consistent forms/dialogs/status chips. Overview highlights usage, recent requests, wallet and quick actions. Responsive tablet/mobile navigation. No external fonts/assets are required.

Considered reconstructing every DOM ID expected by 8 old scripts versus a new buildless UI consuming the same API. Choose the latter: the old scripts have known DOM/global and injection bugs, while a small modular vanilla UI can cover the same features without modifying original services. A framework rewrite adds dependencies with no needed benefit.

Local-only workflow under the Sites skill; no hosted Site or public deployment. User's current request authorizes implementation; design defaults are builder choices and do not wait on a separate approval gate.

## Modes

- Default demo: clearly marked synthetic sample data throughout; no provider API calls. CRUD, search/filter, pagination, preview, forms and simulated workflows run locally and persist only demo state in localStorage. Reset sample data is available.
- Live backend: explicit login/register, bearer JWT and CSRF; proxy API to existing MAIN. Missing services produce clear errors/availability states, never fallback to synthetic success. Demo and live data/session keys are separate.
- No real sending, payment or lookup during our tests. Demo target values use example.test and documentation IP ranges.

Sidebar has grouped entries with tabs inside complex pages. All actions must produce a useful state, validation error or clearly labeled demo result. No empty placeholder page for a covered feature.

## Module contract

ES modules, buildless. `createClient({mode,storage,fetchImpl})` from /data.js returns `mode`, `user`, `api(path,{method,body})`, `login(values)`, `register(values)`, `logout()`, `setMode(mode)`, `resetDemo()`, `health()`; api accepts /api/foo or /foo, returns original-shaped JSON {success,data,...}. Paths and payloads follow existing controllers. Demo resource handlers normalize fields needed by pages; no network from demo api. Live api uses fetch and never manufactures success.

`renderZalo(route,app)` and `renderWorkspace(route,app)` return Promise<{html,bind(container)}> or null. app contains client, ui (helpers), navigate(route), refresh(), modal({title,description,body,submitLabel,onSubmit(values,form),wide}), confirm({title,description,confirmLabel,onConfirm}), toast(message,type), getTab(key,default), setTab(key,value). Bind attaches listeners inside current content. Form action errors are caught and displayed. Shared tab buttons use data-tab-key/data-tab-value; nav links data-nav.

ui exports `h(value)`, `icon(name,size)`, `money(value)`, `number(value)`, `date(value)`, `badge(label,type)`, `pageHead(title,description,actions='',eyebrow='Không gian làm việc')`, `card(title,body,subtitle='',actions='')`, `table(headers,rows,emptyText)`, `field(label,name,options)`, `tabs(key,items,active)`, `empty(title,description,action='')`, `notice(text,type='info')`, `rows(response)`. table cells are HTML and callers must h() user values. field options: type,value,placeholder,required,help,min,max,step,rows,full,options [{value,label}] or strings; type textarea/select supported. buttons use .btn(.primary/.secondary/.ghost/.danger/.small), table .actions, layouts .grid-2/.grid-3/.form-grid/.stack, form footer .form-actions. Every form has native labels/required validation. icon names resolve to a consistent SVG set, unknown names fall back to a small circle.
